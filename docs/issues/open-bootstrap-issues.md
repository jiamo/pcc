# Open bootstrap / self-host issues

**Status:** these are real unresolved problems, not "design choices".
The README's three-stage byte-identical claim is true on its narrow
terms (`cmp pcc2 pcc3` after Mach-O signature normalization on
macOS arm64), but the gates below are open and the bootstrap binary
is not yet a pure-native self-host artifact.

This file is the authoritative tracker of what's still wrong. If a
README or plan paragraph contradicts this file, this file is right.

---

## Issue 1: Bootstrap binary still links `libpython`

**State:** open.

**Evidence:**

```
== gate stage 3, both backends, 2026-04-27 ==
result backend=llvm stage=3 ... libpython=True
result backend=self stage=3 ... libpython=True
```

(`scripts/run_self_backend_bootstrap_gate.py` reports
`links_libpython=True` for every produced binary.)

**Why:** the frontend (parser + type inference + codegen) runs as
CPython-interpreted Python at bootstrap time. Codegen emits
`py_cpy_*` calls for any dynamic-Python idiom in the frontend
sources, which forces the link step to pull `libpython`.

**What this invalidates:** the "self-host" framing is honest only as
"`pcc` builds itself" — not as "the resulting binary has no
external runtime dependency on CPython". A pure-native
`pcc1`/`pcc2`/`pcc3` is *not* what the current bootstrap produces.

**Concrete unresolved sub-issues:** Issue 2, Issue 4, Issue 8.

## Issue 3: Closed-world specialization spike was *not* completed

**State:** open. Codex outlined a 2-week spike with go/no-go gates;
what shipped is a 15-minute negative diagnostic.

**What codex actually proposed
(`docs/plans/closed-world-spike-import-experiment.md` cites him):**

1. Step 1 — fallback categorization probe.  ✅ done (#217)
2. Step 2 — write **two desugar transformers** for the top idioms
   (e.g. `self.runtime["py_cpy_xxx"]` → static field access;
   `getattr(self, "visit_" + kind)(node)` → generated dispatch).
3. Step 3 — measure: if fallback count drops 40-50% in two weeks,
   continue; if 10-20%, stop.

**What I did:** changed `from pcc.llvm_capi.compat import ir` to
`from pcc.llvm_capi import ir` in 4 files, ran the probe, hit
`unbound name 'ir'`, reverted, declared closure convergence
"impossible" and routed it to `hybrid by design`. Step 2 was never
written. Step 3 measurement therefore never ran.

**What this means:** closed-world specialization may or may not
work; we don't know yet. The 15-minute experiment told us *one
specific path* (path-swap of import) doesn't work, not that the
whole approach is dead.

**What it would take to actually finish step 2:** write a Python
AST transformer (~500 lines) that recognizes 2 specific source-level
idioms in `pcc.py_frontend.codegen.layer1` and rewrites them at
build time. Estimated: 1-2 weeks. Not done.

## Issue 4: `ir`-as-scaffold codegen subsystem missing

**State:** open. Identified as the actual cost boundary, not yet
estimated in detail.

**What's there:** `pcc.extern` and `pcc.unsafe` have native
scaffold-lowering rules in codegen — when codegen sees
`extern("getpid", (), c_int)` or `pcc.unsafe.malloc(n)`, it lowers
to native IR.

**What's missing:** the same treatment for `pcc.llvm_capi.ir`:

- ~10 `ir.X` types referenced from layer1 / runtime_abi / class_gen
  / marshal: `IRBuilder`, `IntType`, `PointerType`, `VoidType`,
  `DoubleType`, `Constant`, `Function`, `Module`, `GlobalVariable`,
  `IdentifiedStructType`, `LiteralStructType`, etc.
- ~30 `ir.IRBuilder.*` methods used by layer1: `position_at_end`,
  `append_basic_block`, `store`, `load`, `branch`, `cbranch`,
  `icmp_signed`, `icmp_unsigned`, `call`, `ret`, `ret_void`,
  `sext`, `zext`, `trunc`, `add`, `sub`, `mul`, `sdiv`, `srem`,
  `gep`, `bitcast`, `inttoptr`, `ptrtoint`, `phi`, `landingpad`,
  `resume`, `extract_value`, `insert_value`, `select`, `unreachable`.
- 1,340 `self.builder.X(...)` call sites in `layer1.py`.
- Per-callsite, codegen has to lower the method invocation to
  emitting an IR-text snippet (which is what the Python `ir.IRBuilder`
  implementation does at runtime). This is meta-circular: the
  codegen has to "compile" the very builder calls that the codegen
  itself uses.

**Estimate:** multi-month codegen subsystem, comparable in scope to
`pcc.unsafe` but with a much larger surface.

**What's not been done:** no design doc, no prototype, no scoping
study. Currently nothing in flight.

## Issue 5: `self.builder = None` triggers `Optional[DynType]` infection

**State:** open. Local fix, but blocked behind Issue 4.

**Evidence:** `pcc/py_frontend/codegen/layer1.py:2813` and similar:

```python
self.builder = None
self.current_function = None
self.current_func_def = None
```

These None assignments make `self.builder` an `Optional[IRBuilder]`
in the type inferrer (when Issue 4 lands). Even after Issue 4 is
fixed, codegen will still see Optional and emit dynamic dispatch
unless the None sentinels are replaced (e.g. with a no-op
`_DUMMY_BUILDER` or with a builder/no-builder split state).

Cannot fix this in isolation: without Issue 4, layer1's builder is
already DynType, and the None doesn't make it any worse. Listed here
so it isn't forgotten when Issue 4 starts.

## Issue 10: `py_cpy_main_exitcode` shim still emitted unconditionally

**State:** open, low-priority.

**Evidence:** `pcc/py_frontend/codegen/layer1.py:812` —
`call ... @py_cpy_main_exitcode` is emitted whenever
`emit_cpy_main_exitcode=True` (which is whenever
`libpython_mode in {"on", "auto"}` and AST has any import).
`pipeline.py:1173-1181` says "main only calls
`py_cpy_main_exitcode` when libpython is required". But because
auto + any import → libpython_required, this is the common case for
bootstrap, and contributes to Issue 1.

**Issue 11 is the meta-issue:** the current "writing pcc in pcc-Python"
experience is fragile because most of Python's idioms route through
CPython. Resolving Issue 11 (native builtin dispatch + recursive
stdlib compile) likely unblocks the long tail of Issue 1 reductions
more cleanly than continuing to hand-roll-everything in the current
restricted subset.
