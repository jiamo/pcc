The important design finding is that the self-hosted compiler is not slow
merely because "Layer1 is large". Layer1 size now matters, but the current
sample points at repeated generation of cold exception/traceback IR around
attribute access and post-call checks. More broadly, the stage2 hot path is
still running through Python-object-shaped runtime operations: object fields,
dict lookup, list/tuple containers, refcounting, generic truthiness, and many
small IR object allocations. Rust gets fast compiles from typed fixed-layout
data, arenas/interning, query caches, direct field access, and parallel codegen.
This bootstrap path currently has native machine code, but much of the compiler
data model and IR builder surface still behaves like dynamic Python runtime
traffic.

## Changes Made During This Investigation

### 1. Ownership fixes for raw pointer values

`pcc/py_frontend/codegen/layer1.py` was changed so raw pointer returns from
`pcc.unsafe` helpers are not treated as owned `PyObject*` values.

The key rule added was:

- calls such as `malloc`, `cstr`, `global_addr`, `global_load_ptr`, `ptr_add`,
  `load_ptr`, `memset`, `memcpy`, `getenv`, and call-pointer helpers are raw
  native pointers, not managed Python objects
- `_dataclass_field_value` is also not treated as returning an owned object
- tuple-unpack targets with `DynType` values are no longer blindly marked owned
- pointer-shaped local slots are null-initialized to avoid release of `undef`

This fixed a class of invalid incref/decref behavior where C pointers were
being pushed through the object ownership model.

### 2. Test-level compile cache

`tests/test_py_multi_file_bootstrap_shim.py` now caches the compiled
`pcc/__main__.py` binary within one pytest process.

The cache is intentionally conservative:

- process-local only
- key includes source mtimes/sizes for `pcc/` and `scripts/`
- no reuse across pytest invocations
- disabled by `PCC_TEST_DISABLE_COMPILE_CACHE=1`
- also disabled by `PCC_TEST_COMPILE_CACHE=0`

This is a test-speed fix, not a bootstrap correctness fix.

### 3. `_Scope` type inference rewrite

The original `_Scope` lookup used parallel `names` / `types` lists and linear
lookup. It was first changed to add dict indexes, but that still left extra
list traffic in the stage2 hot path.

The current working-tree version reduces `_Scope` to:

- `bindings: dict[str, Type]`
- `parent: Optional[_Scope]`

This matters for both correctness and speed:

- it removes `list.append` / `list.set` traffic from the hot type-infer path
- it avoids a stage2 heap-corruption crash observed in `_Scope.define`
- it keeps name lookup on direct dict membership instead of repeated method
  dispatch / linear scans

One critical bug was also fixed here:

```python
if parent:
    self.parent = parent
else:
    self.parent = None
```

The compiled runtime can distinguish host `None` and null-ish pointer values
poorly in this path. Normalizing false/null parents prevents a loop over an
invalid parent scope.

### 4. Runtime pointer-shape guards

Runtime object entrypoints were hardened so invalid pointer-shaped values do not
immediately crash the self-hosted compiler:

- `py_incref` / `py_decref`
- `py_instance_get_field` / `py_instance_set_field`
- `py_instance_getattr` / `py_instance_setattr`
- dict get/contains/set/delete/iteration entrypoints

These guards are defensive. They do not prove the producer is correct. They
make the failure mode diagnosable instead of turning every bad value into a
segfault inside a runtime helper.

## Why This Is Not Just "Layer1 Is Too Large"

Layer1 size does hurt:

- larger functions produce larger IR
- they limit incremental reasoning
- they increase optimizer work
- they reduce opportunities for parallel compilation if everything is one
  large module/function body

But the observed stage2 failures and timings point to a more specific design
issue:

- self-hosted type inference uses Python object instances for compiler data
- field access goes through runtime helpers
- scope lookup goes through dict membership
- containers are heap objects with refcount traffic
- a bad pointer can propagate through generic runtime entrypoints before the
  system sees it

Rust is fast for different reasons:

- compiler IR/HIR/MIR structures are fixed-layout typed data
- arenas and interners make object identity and lifetime cheap
- query caches avoid recomputing whole phases
- many lookups are direct indexes, not dynamic dictionary operations
- backend/codegen work can be split across codegen units

The pcc self-host path should move hot compiler structures in the same
direction: fixed fields, direct access, fewer generic PyObject containers, and
phase-level caches. Test caches are useful for local feedback, but they do not
solve the compiler design cost.

### Logging Strategy

Full runtime logging was tried first and was not useful enough:

```bash
PCC_LOG=alloc,gc ...
```

It produced about `1.3GB` / `9.5M` lines in roughly `220s` without reaching
the crash. That style of logging is too broad for this problem. It perturbs the
run, makes the failure slower, and does not identify the producer of a bad
release.

The useful debug strategy was targeted release labeling:

- codegen emits `pcc_debug_check_release(label, obj)` immediately before
  selected `pcc_gc_release` calls
- the checks are compile-time gated by `PCC_DEBUG_RELEASES=1` or
  `PCC_DEBUG_RUNTIME=1`
- the runtime check traps only on suspicious object shape, such as bad
  refcount/type-tag header or stack-looking pointer
- the label carries function/class/local/expression context

Example failure shape:

```text
[BAD_RELEASE] name=local:ClassLowering._maybe_expand_dataclass:inherited_fields ...
```

This is much better than global alloc/free logs because it names the generated
release site before the allocator detects later heap damage.

### GuardMalloc Findings

GuardMalloc was used to make stale/double releases fail earlier:

```bash
DYLD_INSERT_LIBRARIES=/usr/lib/libgmalloc.dylib \
MallocScribble=1 MallocPreScribble=1 \
PCC_DEBUG_RUNTIME=1 PCC_DEBUG_RELEASES=1 \
  <pcc1> --backend self --python-libpython off <probe.py> -o <out>
```

The useful sequence was:

1. `Function.__init__` in `pcc/llvm_capi/ir.py` used a generator/enumerate path
   to build formal arguments. GuardMalloc caught a bad release in that area.
   The code now uses an explicit indexed loop before converting to `tuple`.

2. `_resolve_call_kwargs` exposed a borrowed subscript value being released.
   Raw-scaffold ownership now treats `Subscript` as borrowed.

3. Dataclass expansion exposed a double release:

   ```text
   [BAD_RELEASE] name=local:ClassLowering._maybe_expand_dataclass:inherited_fields ...
   ```

   Root cause: `list(inherited_fields)` on a statically-known `ListType`
   returned the same list object. Both locals were then treated as owned. The
   `list(list_obj)` lowering now performs a shallow copy.

4. `L1CodeGen._hoist_nested_funcdefs:m` exposed a broader ownership mistake:
   in raw scaffold mode, ordinary `FuncType` calls returning object-shaped
   types were treated as definitely owned. That is too aggressive for
   bootstrap/shared helper paths. Raw-scaffold ownership is now conservative:
   literals, class constructors, and known container constructors are owned;
   arbitrary helper calls are not assumed owned solely from return type.

5. GuardMalloc can still find additional raw-string/local issues in small
   debug-only probes. Normal pcc1 and `PCC_DEBUG_RUNTIME=1` pcc1 compile the
   dataclass mini repro successfully, so the old stage2 crash is likely fixed,
   but the ownership model is still fragile enough that the debug path remains
   valuable.

### `chr()` and libpython

`chr()` itself is not the reason for libpython fallback. The native lowering
already exists:

- `pcc/py_frontend/codegen/runtime_abi.py` declares `py_chr_from_i64`
- `pcc/py_frontend/codegen/layer1.py` lowers `chr(int)` to that runtime helper
- `pcc/py_runtime/src/py_str_accessors.c` implements `py_chr_from_i64`

Two direct probes were compiled with `--backend self --python-libpython off`:

```python
def main() -> None:
    print(chr(65))

main()
```

and:

```python
def build() -> str:
    parts = []
    i = 65
    parts.append(chr(i))
    return "".join(parts)

def main() -> None:
    print(build())

main()
```

Both compiled, ran, printed `A`, and `otool -L` showed no libpython dependency.

Therefore, if replacing byte-to-hex formatting with a `chr()`-based
implementation in `pcc/llvm_capi/ir.py` appears to pull libpython in the full
bootstrap closure, the cause is not plain `chr(int)` support. It is likely the
larger self-host shape around that change: string/list construction, join,
indexing, or a fallback classification in the `pcc.llvm_capi.ir` module. That
should get a separate minimized fallback-route repro before blaming `chr()`.

The current `_format_i8_array` implementation intentionally avoids that
question and emits LLVM `c"\XX\YY..."` form with fixed hex-digit indexing. This
keeps the hot constant-format path narrow.

### Why `emit_attr` Is Expensive Here

Every dynamic attribute load currently tends to generate:

- a null check on the returned value
- a pending-exception check
- one propagation block
- one fresh AttributeError construction path
- traceback-frame append calls
- fresh C string globals for function/file/message in several paths
- an ok block and control-flow joins

Every call that can raise similarly tends to generate:

- `py_err_occurred()`
- compare and branch
- optional traceback-frame block
- `py_current_exception()`
- `py_exc_append_frame()`
- branch to function-level error exit

That is semantically defensible for traceback fidelity, but it is a bad shape
for compiling a large self-hosted compiler module: the cold path is cloned at
nearly every attribute and call site. The sample shows the code generator
spending time building the error machinery, not just lowering useful work.

### Mainline Next Steps

Do not mark bootstrap solved until `pcc1 -> pcc2` finishes and the no-libpython
link property is checked again.

The next optimization work should focus on the Layer1 error-path clone first:

1. Pool C strings used by traceback/function/file/error messages so repeated
   frame generation stops creating fresh globals for the same payload. This is
   low risk but only attacks part of the cost.

2. Split "call can raise" from "call cannot raise" in the lowering surface.
   Many IR-builder/runtime helpers used during compilation should not need a
   post-call Python exception check at every call site.

3. Reduce AttributeError-path cloning for statically-known class/field access.
   If the object shape is known and the field load cannot be missing, emitting
   `_emit_attribute_error_if_null` is wasted work.

4. Consider a cold shared helper for dynamic AttributeError construction rather
   than inlining the full raise/frame path at every attribute site.

5. Only after the error-path clone is reduced, revisit splitting
   `layer1.py`. Splitting can help parallel compile and developer reasoning,
   but the latest sample says the immediate time is in cloned dynamic error
   lowering and IR-object churn. Splitting alone will not make those clones
   disappear.

That was wrong for the disabled-log fast path: every refcount/allocation event
paid an environment lookup just to discover `PCC_LOG` was unset.

The runtime logger now caches `PCC_LOG`, `PCC_LOG_FORMAT`, and `PCC_LOG_FILE`
on first use and stores enabled categories as a bitmask. Hot `py_obj.c` sites
were also switched from string-category logging to integer event codes. The
dedicated runtime-log regression still passes:

```bash
/opt/homebrew/bin/timeout 180s env -u LC_ALL uv run pytest \
  tests/test_runtime_log_refcount_weakref_finalizer.py -q -n0
# 3 passed in 1.62s
```

This removed `getenv` from later samples, but it was not the main stage2 cost.

### AttributeError Cold Path Moved Into Runtime

The larger win came from reducing cloned Layer1 AttributeError IR. Dynamic
`py_obj_getattr` now raises `AttributeError` itself when lookup misses, and
Layer1's `_emit_attribute_error_if_null` no longer emits the per-site
"pending exception or synthesize AttributeError" split. `getattr(obj, name,
default)` and `hasattr(obj, name)` clear the expected AttributeError locally
when they intentionally treat a missing attribute as a value.

/opt/homebrew/bin/timeout 300s env -u LC_ALL uv run pytest \

### Remaining Failure

Stage2 is still not solved:

```bash
/opt/homebrew/bin/timeout 900s \
  /tmp/pcc_bootstrap_attrerr.pTcvDN/pcc1 \
  --verbose --backend self --python-libpython off \
  pcc/__main__.py -o /tmp/pcc_bootstrap_attrerr.pTcvDN/pcc2
```

Result:

```text
[pcc.py] type_infer[pcc.py_frontend.type_infer]
[pcc.py] codegen pcc.py_frontend.type_infer
[pcc.py] codegen[pcc.py_frontend.type_infer]
Abort trap: 6
stage2_status=134 elapsed=147s
```

Single-module compile with the same `pcc1` succeeds:

```bash
/opt/homebrew/bin/timeout 240s \
  /tmp/pcc_bootstrap_attrerr.pTcvDN/pcc1 \
  --verbose --backend self --python-libpython off \
  pcc/py_frontend/type_infer.py \
  -o /tmp/pcc_bootstrap_attrerr.pTcvDN/type_infer_single
# single_type_infer_status=0 elapsed=27s
```

That means the crash is not "type_infer.py cannot compile". It is full
multi-file stage2 state, allocation order, or memory pressure exposing an
ownership/heap-corruption bug.

Two lldb attempts changed timing instead of reproducing the abort:

- `MallocNanoZone=0 MallocScribble=1 lldb ...` reached the risky region but
  hit the outer 420s timeout.
- plain `lldb ...` reached `codegen[layer1]` and hit the outer 300s timeout.

Use longer debug timeouts now; 300s is too short for lldb on this workload.

### Current Best Next Step

Build a dedicated debug-label `pcc1`:

```bash
PCC_DEBUG_RELEASES=1 env -u LC_ALL uv run pcc \
  --verbose --backend self --python-libpython off \
  pcc/__main__.py -o /tmp/<debug-dir>/pcc1
```

Then run stage2 with runtime checks enabled:

```bash
/opt/homebrew/bin/timeout 1200s env PCC_DEBUG_RUNTIME=1 \
  /tmp/<debug-dir>/pcc1 \
  --verbose --backend self --python-libpython off \
  pcc/__main__.py -o /tmp/<debug-dir>/pcc2
```

The desired result is an earlier `[BAD_RELEASE]` / invalid decref diagnostic
with the release label, before allocator timing turns it into a generic
`Abort trap: 6`. If that still only times out, the next candidate is adding a
cheap module-boundary heap sanity check after each module compile in
`compile_python_multi`, so the corrupting module can be separated from the
module where malloc finally notices.
